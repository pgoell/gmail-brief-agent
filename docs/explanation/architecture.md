# Architecture

> Status: target state. No code exists yet; this describes the design v1 will implement.

## One-paragraph summary

gmail-brief-agent is a Python CLI, invoked twice daily by cron on a VPS, that triages a Gmail inbox and writes morning and afternoon briefing notes into an Obsidian vault. Orchestration is deterministic end to end; an LLM appears in exactly two fixed places, both with Pydantic-typed structured outputs. Gmail labels are the only state store. There is no database, no queue, and no resident process.

## Pipeline

```
cron (07:00 morning, 16:00 afternoon)
  │
  ▼
fetch unprocessed mail            Gmail API, query -label:Claude/Processed,
  │                               oldest first, per-run cap
  ▼
extract text                      deterministic HTML-to-text, keeps token
  │                               counts sane for long newsletters
  ▼
stage 1: classify + summarize     one LLM call per email, full content in,
  │                               {tier, summary, reason, source_url} out
  ▼
stage 2: compose                  one LLM call over the grouped verdicts:
  │                               dedupe cross-newsletter stories, order by
  │                               importance, write section prose
  ▼
render notes                      deterministic templates; calendar agenda,
  │                               unresolved-items query, counts, and Gmail
  │                               links injected from message IDs
  ▼
write vault notes                 daily-note section + detail briefing note
  │
  ▼
apply Gmail labels                LAST step; see failure semantics
```

## Components

- **CLI entry** (`gmail-brief-agent run morning|afternoon`, `auth`, `eval ...`): argument parsing, config loading, wiring. See the [CLI reference](../reference/cli.md).
- **Google layer**: typed wrappers over `google-api-python-client` for Gmail (list, get, modify labels) and Calendar (agenda for today or tomorrow). Unit-tested against recorded fixtures. Auth is user-consent OAuth; see the [setup guide](../how-to/set-up-google-oauth.md).
- **Extractor**: HTML email bodies to plain text. Deterministic, no LLM.
- **Classifier (stage 1)**: a Pydantic AI agent with a structured output type. Input: extracted email content plus the interest profile as system prompt. Output: tier (see [classification tiers](../reference/classification-tiers.md)), a one-paragraph summary, a reason, and an extracted source URL when present. Calls are independent per email, so they parallelize and each one is a clean eval case.
- **Composer (stage 2)**: a Pydantic AI agent that receives the grouped stage 1 verdicts and returns structured section content. Its job is what only a cross-email view can do: collapse multiple newsletters covering the same story into one item, order items by importance, and write the section prose. It never produces links, file paths, or note structure.
- **Renderer**: markdown templates for the daily-note section and the detail briefing note, matching the formats the vault already uses. All mechanical content (calendar, unresolved items, counts, Gmail message links) is injected here, not generated by an LLM.
- **Label writer**: applies `Claude/Processed` plus the tier label to every triaged message, after notes are written.

## Model tiering

Stage 1 runs on a Haiku-class model: the calls are small, independent, and numerous. Stage 2 runs on a Sonnet-class model: two calls a day where synthesis quality matters. Both are config values, not code. The eval suite is what justifies or revises them; model changes are eval-gated like prompt changes.

## State and failure semantics

Gmail labels are the single source of truth, a property inherited from the incumbent automation and kept deliberately:

- An email is unprocessed if and only if it lacks `Claude/Processed`.
- Unresolved action items are exactly the messages still carrying `Claude/ActionRequired`.

Labels are applied only after vault notes are written. A crash at any earlier point marks nothing processed, so the next run picks up the whole batch again: at-least-once delivery into briefings. The worst duplicate is an item appearing in two briefings, which is benign; the failure mode this ordering prevents is an email being marked processed but appearing in no briefing ever.

Backlog handling is one rule: process oldest first with a per-run cap; the remainder carries to the next run. A vacation pileup drains over a few runs without special modes.

A failed run exits nonzero and logs; it writes no partial notes. Alerting on missed runs is deferred to the observability stack (parking lot).

## Observability contract

The agent's entire observability surface is one line: Pydantic AI's `instrument=True` emitting OpenTelemetry (OTLP) to a collector endpoint on localhost. Traces include prompts and completions, which contain email content; this is why the backing stack is self-hosted.

The Grafana + Tempo + Prometheus + OTel Collector stack is a separate workstream in the server-infra repo, shared by all projects on the VPS. This repo does not carry observability infrastructure. Planned dashboards: cost per briefing, latency, token counts, and tier-distribution drift.

## What is deliberately not here

- An agentic tool-calling loop. The task decomposes into two fixed LLM steps; knowing when not to build a free-running agent is part of the design.
- A database or job queue. Gmail labels already hold the state.
- A resident service. Two runs a day is cron's job.
- Observability infrastructure. It lives in server-infra and outlives this project.
